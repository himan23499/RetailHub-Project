## Traceability Rules

### 1. Every requirement must have test coverage

A requirement should not exist without at least one test case.

Example:

`RHP-102 → AC1 → TC-LOGIN-001`

This means:

**Login requirement → acceptance criterion → actual test.**

### 2. Critical requirements should have multiple layers

For high-risk functionality, testing should not depend only on UI automation.

Example:

`RHP-301 Add Product`

Can be tested through:

* UI
* API
* Database
* Security

This gives us stronger confidence than testing only through the browser.

### 3. Security requirements should have dedicated security tests

For example:

`RHP-702 Authorization`

Should include tests that verify that one customer cannot access another customer's:

* Basket
* Orders
* Account information
* Other protected resources

### 4. Test cases can map to more than one requirement

Sometimes one test proves multiple requirements.

Example:

A complete checkout test may validate:

`RHP-401 Checkout`

and

`RHP-402 Place Order`

and

`RHP-603 Order Data Integrity`

The same automated flow can therefore provide evidence for multiple requirements.

### 5. Status lifecycle

Use the following status values:

| Status         | Meaning                                               |
| -------------- | ----------------------------------------------------- |
| Planned        | Test case identified but not implemented              |
| In Development | Automation is being written                           |
| Ready          | Automation is complete and ready to execute           |
| Pass           | Test executed successfully                            |
| Fail           | Test executed and failed                              |
| Blocked        | Test cannot execute because of dependency/environment |
| Not Applicable | Requirement/test does not apply                       |
| Deprecated     | Requirement or test has been replaced                 |

## Traceability Example

For the login functionality:

**Requirement**

`RHP-102 – Customer Login`

↓

**Acceptance Criterion**

`AC1 – User can log in using valid credentials.`

↓

**Test Case**

`TC-LOGIN-001 – Verify successful login with valid credentials.`

↓

**Automation**

`UI + API`

↓

**Execution**

`Pass / Fail`

↓

**Evidence**

Screenshot + API response + report

↓

**Defect**

If failed:

`BUG-XXX`

This creates a complete chain from the **business requirement all the way to the actual test result**.

## Requirement Coverage Goal

The target for this project is:

* **100% requirement-to-test traceability**
* **100% P0 requirements covered**
* **100% P1 requirements covered**
* Critical security requirements covered by dedicated security tests
* Critical business flows covered at UI/API level
* Important data-integrity requirements covered at DB level
* Automation execution linked to CI/CD results
* Test failures linked to defects where applicable

---

## RTM Maintenance Rule

The RTM must be updated whenever:

1. A new requirement is created.
2. An acceptance criterion changes.
3. A test case is created.
4. Automation is implemented.
5. A test case is removed.
6. A requirement is cancelled.
7. A defect is discovered.
8. A release changes existing functionality.

The RTM is therefore a **living document**, not something created once and forgotten.
